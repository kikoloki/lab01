# AI 协作过程与问题复盘

## 实际发生的协作

本次采用 Codex 进行 vibe coding。学生使用简短自然语言提供课程要求，选择本地 PDF 阅读助手方向，提供模型服务及界面参考，并要求补齐交付材料。Codex 负责将需求拆为参数模型、工具、调用循环和界面，生成代码后执行安装、自动化测试及真实浏览器检查。

简短交互并不意味着没有工程工作：需求到实现之间的大量拆解、验证和修正由 Codex 自主完成。下述记录按已发生的行为整理，既不是逐字聊天记录，也不声称学生手动编写了全部架构或参数。

1. **确定问题与验收范围**：围绕“至少两项工具、标准函数调用、AI 编写基础代码”实现本地阅读助手。以原创的 3 页 PDF 先走通小规模完整流程。
2. **生成基础工程**：Codex 编写 PDF 导入、SQLite 页级索引、Pydantic 参数模型、JSON Schema、模型请求、最多 10 轮的工具编排，以及页码引用核对。
3. **接入实际模型**：学生提供百炼北京地域模型服务，Codex 将密钥仅写入被 Git 忽略的本地 `.env`，使用 `qwen3.8-27b` 进行真实验证。
4. **根据失败证据修正**：安装器暴露依赖版本问题；真实 API 暴露工具选择策略与思考模式不兼容。Codex 分别根据安装结果和官方文档修正，并增加对应检查。
5. **补充可操作界面**：学生提供文档解析产品的界面参考，Codex 加入任务、收藏、PDF 预览、解析文本与原文高亮、JSON、问答、引用跳转及整份导出，并进行桌面和窄屏验证。
6. **整理提交材料**：保留源码、完整系统提示、运行记录和截图，以事实描述 AI 使用方式与局限。

## 技术问题一 生成的依赖版本无法安装

**观察到的现象**：独立 Python 3.9 环境无法安装最初生成的 `python-multipart==0.0.22`，安装器列出的兼容版本最高为 `0.0.20`。

**处理过程**：以实际安装输出为准，将依赖改为 `0.0.20`，重新在项目独立环境安装并运行测试。没有把“代码已生成”当作“环境可复现”。

**经验**：AI 可能生成不适配当前解释器的版本组合，依赖声明必须经过干净环境验证。

## 技术问题二 兼容 API 的参数支持不完全相同

**观察到的现象**：第一次真实接入百炼返回 HTTP 400：

```text
The tool_choice parameter does not support being set to required or object in thinking mode
```

**定位依据**：请求使用了 `tool_choice=required`，Qwen 默认启用了思考模式。百炼官方 Chat API 文档指出 Qwen 对 required 策略存在限制，且支持扩展参数 `enable_thinking`。

**处理过程**：把工具选择策略和思考模式做成配置项。本次使用 `OPENAI_REQUIRE_TOOL_CHOICE=false` 与 `OPENAI_ENABLE_THINKING=false`，发出 `tool_choice=auto`。本地 Pydantic 参数校验、原文证据检查和引用来源检查继续执行，并新增参数回归测试，再运行真实模型检查。

**验证结果**：真实检查提取了本地材料中的 `CEDAR-QX17` 和 37 名参与者，实际执行目录、检索及读页工具。新版界面一次问答为 17.72 秒、5 次工具调用；这只是一次样例，不能表示稳定延迟或整体准确率。

## 如何理解提示工程

本项目的系统提示使用角色限定、明确工具流程和引用格式，让模型围绕外部上下文工作；原文检索落实 RAG；引用校验失败后的修正消息形成基于环境反馈的修正步骤。这些机制可在实际源代码中检查。并未因课件提及 Chain-of-Thought 就虚构使用记录或要求公开隐藏思维过程。

## 分工与局限

学生负责给出目标、选择方向、提供服务及界面参考；Codex 承担主要基础代码、调试和验证工作。API、测试和截图只能证明当前样例可运行，不能证明所有 PDF 都能正确解析。扫描件仍需 OCR；关键词检索会漏掉同义表达；有效页码也不自动证明答案与原文语义一致。

## 可复用的专业提示示例

以下是根据本项目回顾整理的规范化提示写法，供后续开发复用。**不是学生与 Codex 实际对话的逐字记录，也不作为已经发生过这些详细交互的证据。**

### 示例一 从需求写出可验收的实现规格

> 请实现一个仅围绕本地 PDF 回答问题的 Agent。把 PDF 指定页解析和 SQLite 原文检索作为独立工具，使用标准 function calling 与 JSON Schema 接入模型。给工具参数增加 Pydantic 校验。模型先获取文档 ID，再检索和读页；关键结论必须引用物理页码。保留工具名、参数和返回结果，先使用 3 页原创材料完成小规模端到端验证，再扩展界面。

### 示例二 依据报错诊断供应商兼容性

> 真实 API 返回 HTTP 400，提示思考模式不支持 tool_choice=required。请对照该供应商官方文档核对参数支持范围，把差异变为可配置选项，而不是删除本地证据检查。补充回归测试后，使用真实模型重新执行同一份样例，并分别记录模拟测试和真实调用结果。

### 示例三 验证结果来自材料而非模型记忆

> 请用材料中的原创编号和人数作为可核对事实，再提出材料没有提供的成绩提升问题。检查模型是否实际检索和读取页面，引用能否跳回原文，以及无证据时是否明确说明不足。不要把通过少量样例写成总体准确率。

### 示例四 将视觉参考转成可操作工作台

> 参照提供的布局完善工作台：文档列表、上传进度、PDF 与提取文本并排、点击高亮、翻页缩放、当前页 JSON 和 AI 问答。上传进度应来自真实字节传输；问答范围应在服务端限制为当前文档。检查桌面和窄屏布局，截图只展示真实执行。
